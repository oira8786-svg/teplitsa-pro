# Статус разработки

Обновлено: 2026-11-12.

## Подготовлено в репозитории

- Базовая PostgreSQL-схема: хозяйства, членство и роли, теплицы, зоны, культуры, сорта, партии.
- Агрономические операции и снимок проверки безопасности обработок.
- Складские позиции и журнал движений, партии урожая, покупатели, продажи, платежи и расходы.
- Сотрудники, задачи, начисления/выплаты зарплаты, аудит, заметки и каталог единиц.
- Миграция 004 с fail-closed ограничениями: прямые изменения складского журнала, продаж, урожая, платежей, расходов, задач, зарплаты и аудита заблокированы до появления проверенных транзакционных RPC.
- Начальный Flutter dashboard shell и инициализация Supabase через локальные compile-time параметры `SUPABASE_URL` и `SUPABASE_PUBLISHABLE_KEY`.
- Добавлены Flutter-экраны регистрации/входа по email и паролю, первоначального создания хозяйства через RPC `create_organization`, загрузки членства и выбора хозяйства.
- Реализован первый рабочий хозяйственный модуль «Теплицы и зоны»: чтение теплиц/зон выбранного хозяйства, добавление теплицы и добавление зоны с названием, площадью, единицей площади и примечанием. Запись в интерфейсе доступна ролям owner/manager.
- Конфигурационные значения Supabase не зашиты в исходный код и не записываются в репозиторий.

## Что уже выполнено в тестовом Supabase по скриншотам владельца проекта

- Пользователь применил миграции 001, 002, 003 и 004 по порядку; редактор Supabase показал `Success. No rows returned` после каждой.
- В схеме `public` найдено 26 базовых таблиц.
- RLS включён на всех 26 из 26 таблиц.
- Запрос к `pg_policies` вернул 39 политик.
- Дополнительная проверка простых открытых условий выявила только `measurement_units.units_read` с `USING (true)`. Это намеренное чтение общего справочника единиц измерения авторизованными пользователями; сама политика не даёт право записи.
- Провайдер Email включён в Supabase Auth. Владелец проекта сообщил, что включил и сохранил настройки Secure password change и Require current password when updating.

## Не выполнено и не проверено

- Пользователь подтвердил запуск APK на Android, создание тестовой учётной записи и успешный вход через Supabase. Это пользовательская runtime-проверка авторизации; она не заменяет тесты безопасности и ролей.
- Модуль «Теплицы и зоны» записан в GitHub. Требуется проверить на Android обновлённый APK и выполнить пробное добавление тестовой теплицы и зоны.
- SQL-миграции 001–004 применены в проекте по пользовательским скриншотам, но не прошли автоматизированные интеграционные тесты PostgreSQL.
- Проверка RLS пока статическая по каталогам PostgreSQL; нужны реальные тесты изолированных пользователей/ролей двух разных хозяйств.
- Миграция 005 для проверки принадлежности назначенного пользователя к той же организации запланирована, но файл пока отсутствует и не применён.
- Нет транзакционных RPC для проведения складских движений, резервирования урожая, продаж, платежей, расходов, задач и агрономических операций. Для ряда таблиц прямая запись намеренно закрыта миграцией 004.
- GitHub Actions workflow `.github/workflows/android-apk.yml` собирает Android debug APK, выполняет `flutter analyze` и `flutter test`, прикладывает APK как workflow artifact и создаёт prerelease GitHub Release. Первый запуск успешно собрал и опубликовал APK; отдельный шаг анализатора нашёл устаревший сгенерированный тест и deprecated Material import. Добавлен проектный widget test, миграция на официальный `material_ui` и обновлены GitHub Actions до Node 24-совместимых версий. В запуске #11 `flutter analyze` и `flutter test` завершились успешно; Android Gradle build ещё выполняется.
- Нет Storage policies, полноценных автоматизированных тестов, офлайн-БД, очереди синхронизации и разрешения конфликтов.
- Нет импорта/актуализации государственного реестра и официальных регламентов применения СЗР.
- Flutter-клиент ещё не проверен на Android/iOS/desktop.

## Блокирующие задачи перед пилотом

1. Собрать и проверить Flutter-приложение на Android, iOS и desktop.
2. Проверить регистрацию, подтверждение email, вход, выход и создание хозяйства на тестовом Supabase.
3. Добавить и протестировать узкие транзакционные RPC для всех чувствительных операций.
4. Проверить RLS для каждой роли и межорганизационную изоляцию реальными тестовыми пользователями.
5. Добавить Storage policies для приватных вложений.
6. Реализовать формы, чтение/изменение хозяйственных данных, офлайн-хранилище и синхронизацию.
7. Отдельно проверить правовые требования локализации и обработки персональных данных в РФ до production.
8. Не вводить реальные данные сотрудников, покупателей или хозяйства до закрытия перечисленных проверок.

Не считать репозиторий готовой production-системой до закрытия этих пунктов.
