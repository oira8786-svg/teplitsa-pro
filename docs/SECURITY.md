# Безопасность и эксплуатационные ограничения

## Секреты

- Не коммитить .env с секретами, JWT secret, database password, service_role key или access tokens.
- Использовать секреты окружения в CI/деплое.
- При утечке немедленно отозвать/ротировать ключи.

## Supabase

- RLS обязателен на каждой таблице, доступной через API.
- Проверять SELECT/INSERT/UPDATE/DELETE отдельно для каждой роли.
- Не считать скрытие кнопки в UI механизмом защиты.
- Не давать пользователю менять собственную роль или organization_id.
- Для SECURITY DEFINER функций задавать фиксированный search_path и минимальные GRANT.
- Проверять отсутствие рекурсивных RLS-политик.
- Хранилище документов должно быть приватным, с проверкой organization_id в путях/метаданных.

## Персональные данные

Система может содержать ФИО, контакты и сведения о выплатах сотрудников. До реального использования определить оператора персональных данных, правовое основание, сроки хранения, права доступа, порядок удаления/выгрузки и требования применимого законодательства РФ (включая 152-ФЗ). Не загружать реальные данные в тестовую среду.

## Склад и финансы

- Проведённые записи не редактировать и не удалять обычными CRUD-запросами.
- Исправление — отдельная компенсирующая операция.
- Продажи и списания выполнять атомарно.
- Вести аудит: субъект, действие, объект, время, request_id, причина.
- Для денежных операций предусмотреть сверку и журнал статусов.

## Защита растений и безопасность работ

Не генерировать нормы, концентрации, дозировки, сроки ожидания или повторного входа автоматически из общих шаблонов. Значения вводятся/импортируются из проверенного действующего регламента для конкретного препарата, культуры и условий применения в РФ и подтверждаются ответственным специалистом.
