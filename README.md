# ТЕПЛИЦА PRO

Система учёта и управления тепличным хозяйством: теплицы и зоны, культуры и партии, агрономические операции, склад, урожай, продажи, финансы и команда.

**Хозяйство:** Россия, регион Москва.  
**Валюта:** RUB (₽). **Часовой пояс по умолчанию:** Europe/Moscow.  
**Клиенты:** Flutter; Android debug-сборка проверяется через GitHub Actions. iOS и desktop остаются целевыми платформами, их сборки ещё не подтверждены.

## Текущее состояние

В репозитории есть Flutter-клиент с экранами авторизации и выбора хозяйства, теплиц/зон, культур/партий, агрономического журнала и календаря, склада, урожая/продаж, покупателей, расходов, команды/задач, зарплаты и отчётов.

Последняя проверенная Android CI-сборка — тестовая debug APK. Это не production-релиз. Часть серверных действий доступна только через транзакционные RPC; офлайн-режим и приватное файловое хранилище ещё не реализованы.

## Структура

- `app/` — Flutter-клиент.
- `supabase/migrations/` — упорядоченные миграции PostgreSQL/Supabase.
- `supabase/INSTALL_OPERATIONS.sql` — объединённый SQL-скрипт серверных RPC для тестовой установки после миграций 001–004.
- `supabase/tests/` — статические проверки манифеста миграций.
- `docs/` — архитектура, безопасность, статус и инструкции.

## База данных

Основной способ — Supabase CLI:

1. Создать отдельный тестовый проект Supabase.
2. Установить Supabase CLI и выполнить вход.
3. Связать проект: `supabase link --project-ref YOUR_PROJECT_REF`.
4. Проверить список миграций и применить их: `supabase db push`.
5. Отдельно проверить RLS, RPC и транзакционные сценарии на тестовых данных.

Если миграции 001–004 уже применены вручную, для тестовой установки можно использовать `supabase/INSTALL_OPERATIONS.sql` в SQL Editor. Ручной запуск не обновляет историю миграций Supabase CLI; перед последующим `db push` нужно сверить историю, не запускать вслепую.

## Безопасность

- Все бизнес-данные изолируются по `organization_id`.
- Складские движения и проведённые финансовые документы — журнал, а не редактируемый остаток.
- Повторные запросы должны быть идемпотентными; конфликты офлайн-синхронизации нельзя молча перезаписывать.
- В клиент нельзя помещать `service_role` или Secret key. Допустим только публичный publishable/anon key при корректном RLS.
- Не коммитить пароли, токены, реальные данные сотрудников и покупателей.
- Для СЗР не генерировать нормы и сроки: проверять действующую регистрацию и этикетку РФ для культуры и условий защищённого грунта. Непроверенная обработка не считается безопасной для сбора урожая или входа работников.

До завершения проверки БД, резервного копирования, офлайн-синхронизации, приватного хранения файлов и требований 152-ФЗ использовать только тестовые данные.
